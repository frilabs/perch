## 2. Official sources (retrieved 2026-10-05)

- Calendar scopes: <https://developers.google.com/workspace/calendar/api/auth>: `calendar.readonly` "See and download any calendar you can access"; `calendar.events.owned` "See, create, change, and delete events on Google calendars you own".
- `events.insert`: <https://developers.google.com/workspace/calendar/api/v3/reference/events/insert>: scopes include `calendar.events.owned`; `sendUpdates` `all`/`externalOnly`/`none`; caller-supplied `id` must be base32hex (a-v, 0-9), 5-1024 chars, unique per calendar, and "we cannot guarantee that ID collisions will be detected at event creation time"; `dateTime` needs an offset unless `timeZone` is given; reminders: at most 5 overrides, minutes 0-40320; `email` reminders send mail.
- `events.list`: <https://developers.google.com/workspace/calendar/api/v3/reference/events/list> (maxResults default 250/max 2500, `orderBy=startTime` only with `singleEvents=true`, `timeMin`/`timeMax` RFC 3339 with offset, `nextPageToken`).
- `events.get`: <https://developers.google.com/workspace/calendar/api/v3/reference/events/get>.
- `events.patch`: <https://developers.google.com/workspace/calendar/api/v3/reference/events/patch> (`PATCH`, `sendUpdates`, scopes include `calendar.events.owned`; array fields are replaced).
- ETags: <https://developers.google.com/workspace/calendar/api/guides/version-resources> (`If-Match` on update; `412` when the etag no longer matches).
- Errors: <https://developers.google.com/workspace/calendar/api/guides/errors> (`409` duplicate identifier, `412` precondition failed, `429`/`403` rate limits, `5xx`).
- `calendarList.list`: <https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list> (default 100, max 250).
- `people.connections.list`: <https://developers.google.com/people/api/rest/v1/people.connections/list> (only `people/me`; `personFields` required; `pageSize` 1-1000, default 100; `pageToken` requires identical other parameters; scopes `contacts`/`contacts.readonly`; `sources` default contact + profile).
- `people.get`: <https://developers.google.com/people/api/rest/v1/people/get>.
- OpenID Connect: <https://developers.google.com/identity/openid-connect/openid-connect> (`openid email` scopes; `email`, `email_verified`, `sub` claims; use `sub`, not email, as the identifier; userinfo endpoint `https://openidconnect.googleapis.com/v1/userinfo` from the discovery document, which Perch hard-codes instead of fetching).

These are documentation checks, not live validation.

## 3. Authorization model

Still **single operator** (see `docs/EMAIL_MILESTONE.md` §2). This increment adds no multi-user isolation.

- **Operator** (global HTTP token, plain `perch serve --stdio`): read-only. Gets the five Calendar/Contacts read tools for every connected `gprod-…` account and `googleProductivity[]` in `perch_list_accounts`. Never gets `calendar_create_event`/`calendar_update_event`; the service denies writes for it anyway (`capability_denied`). Drive/Notion/mail tools are unchanged.
- **Client grants** (`perch client add --allow CAPS --account ID ...`):
  - `calendar_read` → `calendar_list_calendars`, `calendar_list_events`, `calendar_get_event`;
  - `contacts_read` → `contacts_list`, `contacts_get`;
  - `calendar_write` → `calendar_create_event`; `calendar_update_event` is listed only with `calendar_write` **and** `calendar_read` (the update reads the event first and returns it);
  - mail capabilities `read`/`draft`/`send` apply only to mail accounts, Calendar/Contacts capabilities only to `gprod-…` accounts. `perch client add` refuses grants where a capability family has no matching account or an account has no matching capability, so a calendar grant never carries mail access and vice versa.
- **Metadata:** a client's `perch_list_accounts` contains `mail` only with a mail capability and `googleProductivity` only with a Calendar/Contacts capability; per account only the granted services and their provider capabilities. Email-milestone (mail-only) clients see exactly what they saw before.
- **Checks per call, in this order, before any provider I/O:** (1) the grant is re-resolved from the store (id + token hash; `grant_revoked` after `perch client remove`, also in long-lived stdio sessions; HTTP additionally answers `401`); (2) the principal holds the capability for that account (an ungranted id and a nonexistent id fail identically); (3) the account exists; (4) the onboarding selection **and** the scope Google granted at onboarding allow it; (5) right before the request, the scope Google reported with the current access token (refresh responses carry `scope`) still includes it, otherwise `provider_scope_missing` without a request. The stored `allowCalendarWrite` flag alone never enables a write.
- **Defence in depth:** `POST …/events` and `PATCH …/events/{id}` are only reachable with the `calendar_write` route tag; there are no `DELETE`/`PUT`, move, import, quickAdd, instances, watch or ACL routes.

## 4. Provider details

- **Origins** (fixed, `redirect: "error"`, 30 s timeout, 5 MiB JSON cap as before): Calendar `https://www.googleapis.com/calendar/v3/…`, People `https://people.googleapis.com/v1/…`, userinfo `https://openidconnect.googleapis.com/v1/userinfo`.
- **Path allowlist:** `GET /calendar/v3/users/me/calendarList`; `GET|POST /calendar/v3/calendars/{cal}/events`; `GET|PATCH /calendar/v3/calendars/{cal}/events/{event}`; `GET /v1/people/me/connections`; `GET /v1/people/c<digits>`.
- **Ids:** calendar ids `[A-Za-z0-9._+#-]` with at most one `@` (holiday calendars contain `#`), encoded with `encodeURIComponent`; the allowlist admits only `%40`, `%2B`, `%23`, so no encoded `/`, `.` or `%` reaches a path. Event ids: base32hex, optionally with the recurring-instance suffix `_YYYYMMDD` or `_YYYYMMDDTHHMMSSZ`. Contacts: only `people/c<digits>` (never `people/me` or Google account ids, so `contacts_get` cannot look up other people's profiles).
- **Calendar reads:** `events.list` always uses `singleEvents=true&orderBy=startTime`. Default `timeMin` is "now"; because Google requires identical parameters on every page, the effective `timeMin` travels inside Perch's cursor. Fan-out without `accountId` reads each account's `primary` calendar; `calendarId` requires `accountId`. Results are ordered per account, not merged globally by time. `start`/`end` are returned exactly as Google sends them; all-day events carry `allDay: true` and `endExclusive: true` (end date = day after the last day); `calendarTimeZone` comes from the list response. Descriptions are cut at 8192 characters (`descriptionTruncated`), attendees at 50 (`attendeesOmitted`).
- **Contacts reads:** `personFields` from an allowlist (`names, nicknames, emailAddresses, phoneNumbers, organizations, addresses, birthdays, biographies, urls, relations, events, memberships, metadata`; default `names,emailAddresses,phoneNumbers,organizations`), `sources=READ_SOURCE_TYPE_CONTACT`, page size 1-100 (default 50), optional `sortOrder`. Only the requested fields are passed through. **No search and no full-text claim:** `contacts_list` pages through all contacts.
- **Pagination/partial results:** the existing fan-out cursor (per-account upstream cursor, 3 retries, `partial`/`errors[]`).

## 5. Calendar writes: the exact constrained subset

- **Allowed fields:** `summary` (1-1024 chars), `description` (≤ 8192), `location` (≤ 1024), `start`, `end`, `transparency` (`opaque`/`transparent`), `visibility` (**only** `private` or `confidential`), `reminders` (`useDefault` must be `false`, plus ≤ 5 **popup** overrides, 0-40320 minutes). No control characters; request body ≤ 16 KiB.
- **Private and silent by construction (review fix 2026-10-05):**
  - Google's `visibility: "default"` (also what Google applies when the field is missing) *inherits the calendar's sharing*. An owned calendar, including `primary`, can be shared publicly with full details. Perch therefore refuses `default` and `public` and never omits the field. **Create** sends `visibility: "private"` unless the caller sends `confidential`. Google documents `confidential` as "The event is private. This value is provided for compatibility reasons."
  - Calendar default reminders (`useDefault: true`, also applied when `reminders` is missing) can include **email** reminders. Perch refuses `useDefault: true` (with or without overrides) and never omits the field. **Create** sends `reminders: {useDefault: false, overrides: []}` unless the caller sends popup overrides. `overrides` is always sent as an explicit array.
  - **Update** returns an event that is private and popup-only, in **the same PATCH** as the requested change. There is no second request, and nothing is refused just for this reason:
    - If the caller does not set `visibility` and the existing event is not `private`/`confidential` (that is: `public`, `default`, missing or anything else), the PATCH adds `visibility: "private"`.
    - If the caller does not set `reminders` and the existing event does not have exactly `useDefault: false` with only valid popup overrides (default reminders, missing reminders, email or malformed overrides), the PATCH adds `reminders: {useDefault: false, overrides: [the existing valid popup overrides]}`.
    - Caller-supplied `reminders` always carry an explicit `overrides` array (`[]` if none were given). Google's patch merges nested objects, so an omitted array would keep old email overrides.
    - Consequence: updating an existing public event makes it private. On `rejected`/`precondition_failed` nothing was changed, so the event remains as it was. `indeterminate` means re-read it.
  - Detail text of `created`/`updated`: "No invitations or updates were sent to anyone … private … popup reminders only". Perch does not promise "no notifications" beyond that. Popup reminders are notifications on the user's own devices by design.
- **Refused with an explicit reason** (also at the MCP boundary; write tools use loose input objects so the strict service parser sees every field): `attendees`, `organizer`, `creator`, `conferenceData`, `hangoutLink`, `attachments`, `recurrence`, `recurringEventId`, `guestsCan*`, `anyoneCanAddSelf`, `sendUpdates`, `sendNotifications`, `source`, `extendedProperties`, `gadget`, `id`, `iCalUID`, `eventType`, `status`, `sequence`, `acl`, the special event-type properties; any other unknown field → `Unsupported field`.
- **Times:** both all-day (`date`, `yyyy-mm-dd`, valid calendar date, no `timeZone`) or both timed (`dateTime` RFC 3339 with offset, or without offset plus an IANA `timeZone`); end strictly after start, compared as instants (DST-aware for wall times in a time zone); at most 366 days. Years 0001-9999 are accepted. Every instant (all-day, timed, wall time in a zone, events.list `timeMin`/`timeMax`) is computed with full-year UTC construction (`utcMs`: `Date.UTC` followed by `setUTCFullYear`). `Date.UTC` alone maps years 0-99 to 1900-1999, which bypassed the ordering and 366-day checks for timed values before the review fix.
- **Every write** is sent with `sendUpdates=none` and without `conferenceDataVersion`/`supportsAttachments`. With no attendees, Google has nobody to invite. Google warns that `none` can affect syncing to *external* guests' calendars, which does not apply without guests. "created"/"updated" mean accepted by Google, not a sync or delivery confirmation.
- **Create idempotency:** `requestId` (8-128 chars `A-Za-z0-9._:-`, required) → event id `perch` + base32hex(SHA-256(`accountId`, `calendarId` as given, `requestId`)). The same triple always yields the same id. Outcomes:
  - `created`: Google returned 2xx;
  - `conflict`: Google returned 409. An event with that id already exists, e.g. from an earlier call whose response was lost. Ids of deleted events stay taken. Nothing new was created;
  - `rejected`: other 4xx; not created;
  - `indeterminate`: network loss, timeout or 5xx after the request left. Perch **never retries**. The user can check with `calendar_get_event` using the returned `eventId`, or repeat the call with the **same** `requestId` and the same `calendarId` string, which either creates the event once or yields `conflict`.

  Limits: `primary` and the calendar's email id are different strings, so mixing them changes the id. Google states it cannot guarantee collision detection at creation time.
- **Update:** `etag` required (from `calendar_get_event`/`calendar_list_events`). Perch first reads the event:
  - etag differs → `precondition_failed` with `currentEtag`, no write;
  - only private events of the user are changed: no attendee other than the user, organiser is the user (`organizer.self === true`; a **missing** organizer object is refused too, fail closed), not part of a recurring series or an instance, event type `default`, not cancelled. Otherwise `unsupported_event`, no write;
  - a single changed `start`/`end` is validated against the other existing value.

  Then exactly one `PATCH` follows, with `If-Match: <etag>` and `sendUpdates=none`, carrying only the changed fields plus, if needed, the `visibility`/`reminders` hardening described above. Outcomes: `updated` (with the new etag); `precondition_failed` (412: changed meanwhile); `rejected`; `indeterminate`, where re-reading shows whether it was applied (new etag with your values = applied).

## 8. Known limitations and exact remaining scope

- **Not live-verified:** no real Google consent, token, Calendar or People call. Request/response shapes come from the primary docs (§2) and the MOCK only. In particular unverified live: whether Google echoes `email` as `userinfo.email` in the token response (both forms are accepted); that `calendar.events.owned` is accepted together with `calendar.readonly` on the consent screen of an unverified app; the exact 409 behaviour for reused ids of deleted events.
- **Multi-user ownership isolation is NOT part of this increment** and stays an open acceptance criterion: per-user ownership of credentials, requests, files, sessions and results, no global token that exposes all accounts, and explicit cross-user denial tests. Client grants narrow one operator's access; they do not separate users. Do not deploy Perch as a shared multi-user service.
- **Calendar:** no attendees/invitations/notifications, no recurring events (create or update of series/instances), no delete/move, no conferencing/attachments, no free/busy, no writes to calendars the account does not own (the scope is `calendar.events.owned`); event ids outside base32hex (+ instance suffix) are refused; fan-out reads only each account's `primary` calendar and does not merge results across accounts by time; `timeZone`-less `dateTime` values in responses are passed through as Google sends them.
- **Idempotency:** per (`accountId`, `calendarId` string, `requestId`); `primary` vs. the calendar's email id produce different ids. Google does not guarantee collision detection at creation time.
- **Contacts:** read-only, contact sources only, no search, no contact groups, no other-contacts/directory, page size ≤ 100.
- **Write subset semantics:** an update of an existing public/default-visibility event, or of an event with calendar default or email reminders, **changes** it to private and popup-only (same PATCH). Callers cannot opt out. Popup reminders still notify the user's own devices. Google may still notify the owner about their own calendar for reasons outside the event body (for example their own notification settings); this was not live-verified.
- **Smoke guard scope:** it covers the smoke child processes (`fetch` and `net.Socket#connect`). Unit tests use injected mock transports and do not use the preload. UDP/child-process network use is not intercepted; Perch uses neither.
- **Grants:** the tool list of a running stdio session is not refreshed after narrowing; tools no longer granted stay listed but fail closed (as in the email milestone).
- **Google policy:** in Testing status refresh tokens expire after 7 days; `contacts.readonly` and `calendar.*` scopes are sensitive and need verification for a published app.
- **User tasks for a live test:** enable Calendar API and People API, add the scopes to the consent screen, add test users, run `perch google-productivity add --services calendar,contacts --allow-calendar-write`, create a client grant, then create and update one private test event on your own calendar and check that no guest/notification exists.
